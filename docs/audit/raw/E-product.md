## 1. Executive verdict: CONDITIONALLY READY (as a labelled demo of one seed cluster), NOT READY against the stated end goal

What works and is honest: ontology search (diseases, genes, HPO terms, synonyms, typo suggestions); per-disease pages built from MONDO/HGNC/HPO; HPO symptom-similarity with the exact shared HPO terms; real ClinicalTrials.gov studies and GARD patient groups; labelled stored paper claims (59 claims in `data/store/atlas.db`) with verbatim quote, DOI link, "found by AI / AI hypothesis / unreviewed" labelling; a real MuJoCo workflow checker with five fixtures that fail for the right reasons and disclose "biology not modeled".

What does not meet the end goal (the user journey the brief describes):
1. The headline cross-disease story (CLN3 disease and Niemann-Pick type C share lysosomal cholesterol build-up, PMID 37245481) is stored and reachable via `GET /api/entities/MONDO:0008767/routes?to=MONDO:0018982`, but Niemann-Pick type C is absent from CLN3's connections list, and the new category "literature-supported lead" is never produced. The frontend never calls `/routes`.
2. There is no free-text question answering (`POST /api/explain` is a canned stub that ignores the question and returns `sentences: []`).
3. There is no symptoms-only, multi-term or variant search. `seizures vision loss ataxia` returns 0 results; HGVS/rsID return 0 results.
4. `POST /api/uploads` is a fixed fixture: it ignores the request and stores nothing.
5. Every response, including real-data responses from `/api/search`, carries a top-level `_synthetic` string saying "SYNTHETIC demo dataset ... makes NO biological claim", which is false for real hits.
6. The only contradictory-evidence, VUS, and "evidence-linked simulation" examples are synthetic (`SYN:`) fixtures.

No Critical (unsafe clinical claim / fabricated evidence) defect was found. The stored claims I sampled carry real quotes and DOI-style URLs; I did not open the papers (see section 7).

## 6. Findings with severity

No Critical findings.

### High

**H1. The advertised CLN3<->NPC connection is not in the connection lists, and the new "literature-supported lead" category is unreachable.**
`src/atlas/search.py:101-124, 292`: `connections()` runs the engine over `self.store`, an in-memory `PublicStore` built from HPO gene-disease rows, not over `data/store/atlas.db` (read separately by `api/claimstore.py`, only used by `/graph`, `/routes`, `/claims`). Hence paper claims never influence `category`, `compatibility_flags`, or candidate selection; candidates come from phenotype overlap (CLN3 list: CLN1/5/9, Tay-Sachs, SCA7, PKAN, MELAS...; NPC list does not include CLN3).
Repro: `curl localhost:8105/api/entities/MONDO:0008767/connections | grep -c 0018982` prints 0; `curl 'localhost:8105/api/entities/MONDO:0008767/routes?to=MONDO:0018982'` returns 3 routes with 4+ cited claims.
Impact: the README and DEMO_SCRIPT beat "CLN3 disease page, the related diseases list ... Niemann-Pick type C appears" (DEMO_SCRIPT.md line 11) does not happen. The product's best evidence is invisible in the main list and a user is told only "symptom-level lead" for unrelated diseases.
Fix: inject the stored claims into the engine's claim set (read-only) so stored-claim endpoints seed candidates (union with phenotype neighbours) and `categorize()` can return "literature-supported lead"; add an API test asserting NPC appears in CLN3's candidates with category "literature-supported lead" and ≥1 supporting claim; add a Playwright test for it. Also update DEMO_SCRIPT, which says it was "written from the code and tests, not from a recording" and whose beat 2 is currently false.

**H2. Free-text question endpoint and uploads are stubs that return success-shaped empty/fixed responses.**
`routes.py:385-399`: `/explain` returns `sentences: []` for any question (200 OK); `/uploads` returns a canned `quarantined:true, claim:null` for any body. Neither is wired in the frontend (grep). A client or judge probing these endpoints would conclude they work but found nothing.
Repro: scenario 9 and 27 above.
Fix (minimum): return HTTP 501 with `{"detail":"not implemented in this build"}` or an explicit `{"status":"not_implemented"}`, remove them from the OpenAPI doc, and state it in the README; or implement a grounded Q&A that answers only from stored claims, with `MODEL-GENERATED HYPOTHESIS` labels, and an upload that validates, stores as `lab_reported` + `unreviewed` + contributor, and is excluded from `category` computation and public search by default.

**H3. No symptoms-only, multi-term, sentence, or variant input.**
`SearchIndex.search` matches names only; scenario 7/8/8c return 0 results with no guidance. This is a core part of the brief ("when no disease is named, candidate disease hypotheses plus relevant genes/phenotypes/mechanisms/tissues").
